# Audit Targeting Engine

**When you can only inspect a fraction of what moves through your operation, which fraction should it be?**

This repo answers that question end to end: it ranks every unit by probability of error, measures how many errors that ranking actually catches at a realistic inspection budget, and converts the result into annual dollars.

On the included dataset, inspecting the **top 2% by model score catches 8.4x more errors than random sampling** and **6.6x more than the value-based rule most operations teams run today**. Matching the incumbent's catch rate takes **86% less inspection labor**.

> **The data here is synthetic.** It is generated by `src/generate_data.py` with a known error mechanism, so every result is reproducible and nothing proprietary is involved. The method is the point, not the numbers. Real engagements start by re-running this on your data.

---

## The problem this solves

Most quality operations have the same shape. There is more to inspect than there is capacity to inspect it, so something has to choose. That something is usually one of three things:

- **Random or rotational sampling.** Defensible, statistically clean, and it finds errors at exactly the base rate.
- **A value rule.** Inspect the expensive items, the big quantities. Reasonable, built by people who know the operation, and it barely beats random because cost and error risk are only weakly related.
- **Supervisor judgment.** Sometimes excellent, never auditable, and it leaves when the supervisor does.

A model beats all three not because it is smarter but because it can weigh twenty signals at once and update itself as conditions change.

## Results

All figures are on a 36,000-pick holdout, split forward in time, with a 3.8% error rate.

| Strategy | PR-AUC | Lift @ 2% | Lift @ 5% | Errors caught @ 5% |
|---|---|---|---|---|
| Random sampling | 0.037 | 0.9x | 0.9x | 4.7% |
| Incumbent rule (value x qty) | 0.044 | 1.3x | 1.3x | 6.6% |
| Boosted, raw features only | 0.157 | 6.9x | 5.2x | 26.1% |
| Logistic regression, engineered | 0.186 | 8.1x | 5.9x | 29.7% |
| **Gradient boosted, engineered** | **0.195** | **8.4x** | **5.9x** | **29.5%** |

### Three things worth noticing

**The incumbent rule is barely better than random.** Value and error risk are only weakly correlated, so auditing expensive items feels rigorous and is close to a coin flip. This is the single most common finding in this kind of work, and it is usually the moment a client's mind changes.

**Feature engineering is worth more than model choice.** The same boosted model goes from 6.9x to 8.4x purely on engineered features. That gap is larger than the gap between logistic regression and gradient boosting.

**Logistic regression gets within a few points of the boosted model.** Once the interactions are engineered into features, a linear model captures most of the available signal. That matters, and I would say so to a client rather than selling complexity: if your team needs to defend every flagged unit to a skeptical operator, the interpretable model may be the better deployment even though it scores slightly lower. The boosted model's real edge shows up at the tightest budgets, which is where it counts if capacity is scarce.

## Turning lift into dollars

Lift is not a business outcome. `src/cost_model.py` converts a ranked list into total cost of quality, which is inspection labor plus the cost of errors that escape.

![Cost curve](outputs/cost_curve.png)

Assumptions are explicit and adjustable in `CostAssumptions`, and they are meant to be replaced with real figures in week one of an engagement:

| Assumption | Default |
|---|---|
| Inspection time per unit | 4.5 min |
| Loaded hourly rate | $27 |
| Cost of a missed error | $42 |
| Daily pick volume | 40,000 |

Under those defaults the model has a genuine cost optimum near a 20% inspection budget, while the incumbent rule's cost curve is nearly flat, meaning more inspection buys almost nothing. That flat curve is the real indictment of rule-based targeting.

## Method notes

The parts that matter are mostly not the model.

**Forward-in-time splitting.** `features.time_split` splits by sequence, not at random. A random split lets picks from the same shift land on both sides and inflates every metric. Audits are scheduled forward in time, so evaluation has to be.

**No leakage through aggregates.** The picker error-rate feature is an expanding mean, shifted so a row never sees its own outcome, and it is suppressed until a picker has 20 prior picks. Leaky aggregate features are the most common way a model like this looks excellent in development and fails in production.

**Shrunk picker risk.** A picker with 21 picks and 2 errors is not worse than one with 900 picks and 60. `picker_risk_shrunk` blends toward the population mean with a prior weight of 60 picks.

**Deliberate noise controls.** `tote_color`, `label_printer_id`, and `day_of_month` are generated with no relationship to the target and left in the feature set on purpose. If any of them ranked highly, something would be wrong. The lowest-ranked control sits at position 38 of 39.

![Feature importance](outputs/feature_importance.png)

**Permutation importance, not gain.** Measured on the holdout against average precision, so importance reflects the metric the business cares about and is comparable across model backends.

**No resampling and no class weighting.** The target is ~4% positive. Reweighting distorts predicted probabilities, and since the deliverable is a ranked list against a capacity budget rather than a hard classification, calibrated probabilities are worth more than a better threshold on a metric nobody uses. Calibration is checked by decile in `outputs/calibration.png`.

**Accuracy is never reported.** On a 4% target, predicting "no error" every time is 96% accurate and useless.

## Running it

```bash
git clone https://github.com/laurenashapowell/audit-targeting-engine.git
cd audit-targeting-engine
pip install -r requirements.txt
python run_pipeline.py
```

About a minute on a laptop. Every table and chart in this README is regenerated into `outputs/`.

XGBoost is the intended backend. If it is not installed, the pipeline falls back to scikit-learn's `HistGradientBoostingClassifier`, which is a real gradient booster and lands within a couple of points. The committed outputs were produced with the fallback; `outputs/headline_results.json` records which backend ran.

## Layout

```
src/generate_data.py   synthetic picks with a known error mechanism
src/features.py        feature engineering, leakage rules, time split
src/model.py           XGBoost with sklearn fallback, plus logistic reference
src/evaluate.py        lift, capture, calibration, and the two baselines
src/cost_model.py      ranked list into annual dollars
run_pipeline.py        end to end
outputs/               charts, metrics, cost analysis
```

## Applying this elsewhere

The features are specific to fulfillment. The structure is not. The same spine applies wherever capacity is scarce and something has to be prioritized:

- Fraud and transaction review queues
- Insurance claims triage
- Vendor and supplier risk ranking
- Quality inspection sampling in manufacturing
- Compliance and account review prioritization

What changes is the feature layer. What stays is the ranking frame, the leakage discipline, the honest baseline, and the cost translation.
